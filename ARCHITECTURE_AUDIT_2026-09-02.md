## 1. Что это вообще, одним взглядом

Один бизнес, три довольно независимых системы под одной крышей:

1. **Каталог-агрегатор** (сайт myavto-agregator.ru) — компании-импортёры авто, лиды, отзывы. Данные живут в Google Sheets, сайт — статический HTML со встроенным JS-массивом компаний, генерируется скриптом и пушится в git.
2. **Bot-слой каталога** (telegram_bot_service.py) — Flask API для сайта (заявка/отзыв/визит) + Telegram-бот, который сводит клиента и компанию.
3. **Контент-конвейер** (userbot_parser.py + auto_montage.py + watermark_video.py) — отдельный юзербот, который репостит видео/фото машин из чужих Telegram-каналов в свои каналы @MY_Avto5/@My_Avto_Optimal, с удалением чужого бейджа и авто-монтажом. Плюс отдельный feedback_bot.py — бот обратной связи именно для покупателей из этих каналов.

Эти три системы почти не пересекаются по коду (кроме общего `sheets_client.py` для каталога) — это **хорошо**, разная аудитория, разная логика, нет смысла их сливать. Но внутри каждой есть накопившиеся за месяц с лишним точечных правок швы, которые стоит подчистить.

## 2. Карта связей

```
Google Sheets (единственный источник правды по каталогу)
        │
        ├── company_agent.py (cron, VPS, раз в сутки)
        │     ищет новые компании (tgstat + DuckDuckGo) → скрейпит сайты →
        │     достаёт ИНН/телефон/соцсети → пишет строку в Sheets
        │
        ├── update_site.py (тот же cron, следующим шагом)
        │     читает Sheets → достаёт ЕГРЮЛ-статус (verify_egrul.py, ТОЛЬКО
        │     здесь, не в company_agent.py) → перегенерирует массив COMPANIES
        │     внутри app.js → git commit + push
        │           │
        │           ├── GitHub Pages — основной хостинг сайта
        │           └── VPS REG.ru — зеркало для рунета/Яндекса,
        │                 git pull раз в 10 минут по cron
        │
        └── telegram_bot_service.py (Flask + бот, отдельный процесс на VPS)
              GET  companies ← Sheets (кэш 90с)
              POST /api/mass-request → bot_state.json → уведомление
                    админу (Telegram + email) → бот пишет подходящим
                    онбордившимся компаниям → компания отвечает боту →
                    бот пересылает ответ клиенту
              POST /api/review → отдельная вкладка Sheets (модерация
                    вручную, moderate_reviews.py)
              POST /api/visit → visits.json (счётчик, не связан с остальным)

Отдельно, без связи с каталогом:
  userbot_parser.py (systemd, VPS) — слушает чужие Telegram-каналы →
    парсит текст (SOURCE_PARSERS) → чистит фото от бейджа (свой встроенный
    OCR, remove_watermark()) → auto_montage.py делает короткое вертикальное
    видео (свой OCR через watermark_video.py, который ИМПОРТИРУЕТ
    userbot_parser.py целиком ради одной OCR-функции — см. п.4) →
    постит в @MY_Avto5/@My_Avto_Optimal

  feedback_bot.py (systemd, VPS) — отдельный бот, отдельный токен,
    отдельный state-файл, собирает анкеты покупателей из тех же каналов
```

## 3. Что уже сделано правильно (не трогать)

Чтобы не создалось впечатление, будто всё плохо — несколько решений, которые явно продуманы и правильны:

- **`--workers 1 --threads 4`** в telegram-bot.service — осознанно, с комментарием в коде, почему нельзя больше одного воркера (Telegram-поллинг и `bot_state.json`-offset живут в памяти процесса). Комментарий и реальный конфиг совпадают.
- **Атомарная запись state** (tmp-файл + `os.replace`) — везде, где есть локальный JSON-стейт, с явным комментарием про баг с обрывом записи, который это чинит.
- **Философия "лучше пропустить, чем испортить"** в OCR/бейдж-логике (и фото, и видео) — риск показать чужой бейдж всегда выбирается в пользу пропуска кадра/плана, а не публикации с ошибкой.
- **`table_range="A1"` при записи в Sheets** — намеренный фикс от расползания колонок, с объяснением в коде.

### Средний приоритет

5. **watermark_video.py импортирует весь userbot_parser.py (129 КБ) ради одной OCR-функции** (`_find_badge_box` и её соседей — `_badge_corner_regions`, `_fuzzy_badge_word`, `_levenshtein`, `_ocr_badge_hits`, строки 927-1327 userbot_parser.py). Это тянет за собой Telethon-логику, парсеры источников, работу с очередями — всё, что video-модулю не нужно. Логичнее вынести детект бейджа (общий для фото и видео) в отдельный небольшой `badge_ocr.py`, который импортируют оба места. Заодно это симметрично тому, что video-часть уже вынесена в свой файл, а photo-часть — нет.

6. **Дублирование ~80 строк логики обогащения контактов** между веткой tgstat и веткой DuckDuckGo в `company_agent.py` (строки ~2193-2234 и ~2497-2574) — одна и та же последовательность `find_map_links → find_social_links → find_marketplace_links → extract_extra_contacts_from_text → backfill_from_sources`, только с разными именами переменных. Именно такое дублирование — вероятная причина повторяющегося в TASKS.md паттерна "починил в одной ветке, забыл про другую". Стоит вынести в одну функцию `enrich_and_backfill(...)`.

7. **7 отдельных списков-исключений** в company_agent.py (`generic_brands`, `VK_RESERVED_PATHS`, `INSTAGRAM_RESERVED_PATHS`, `MAX_RESERVED_PATHS`, `KNOWN_PLATFORM_OWN_ACCOUNTS`, `EMAIL_JUNK_*`, `BLACKLIST`) решают один и тот же класс проблемы ("это служебная страница платформы, а не компания") — видно по комментариям "тот же класс проблемы", повторяющимся по всему файлу. Стоит свести в один словарь `{платформа: {reserved_paths, own_accounts}}`.

8. **telegram_bot_service.py и feedback_bot.py дублируют весь Telegram-транспорт**: отправку сообщений, чтение обновлений (`getUpdates`+offset), парсинг прокси/конфига, атомарную запись state-файла — независимо друг от друга, почти один в один. Разные аудитории — это правильно, но транспортный слой одинаковый. Вынести в общий `tg_common.py` (send/poll/proxy-config/atomic-state) — тогда, например, будущий фикс на 429-ошибки Telegram (сейчас не обрабатываются нигде, см. п.9) чинится один раз, а не в двух местах.

9. **Нет обработки Telegram 429 (rate limit)** ни в одном из ботов — при рассылке заявки нескольким компаниям разом (`handle_start` в telegram_bot_service.py) частый сценарий: часть сообщений молча не уйдёт, в логах — просто warning. Стоит добавить retry с backoff хотя бы в общий `tg_send`.

10. **`notify_admin` — единственный канал видимости новых заявок** — шлёт в Telegram И на почту без проверки, что хотя бы один канал реально сработал. Если оба недоступны одновременно (сеть/прокси легли, и одновременно неверный `mail_config.env`) — заявка просто потеряется без каких-либо следов, кроме строчки в journalctl. Стоит писать резервную строку в отдельный лог-файл, если ОБА канала не отработали.

Похоже на остаток эксперимента с CSS-тулингом (`@csstools`, `bidi-js`). Если не используется — можно удалить, ничего не сломается (не в git).
