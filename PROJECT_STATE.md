## Что это
Публичный агрегатор компаний по импорту авто в СНГ (Китай, Корея, Япония, США,
ОАЭ, Европа). Сайт: myavto-agregator.ru. Репозиторий: GitHub
`lesnikovmn-svg/myavto-agregator` (публичный).

## Архитектура
Google Sheets (база данных) → Python-скрипты на Маке → генерируют встроенный
JS-массив в `index.html` → git push → GitHub Pages (основной источник) +
VPS REG.ru (зеркало, отдаёт сайт для рунета/Яндекса).

## Инфраструктура
- **Домен**: myavto-agregator.ru, регистратор и DNS — REG.ru.
- **VPS**: REG.ru, IP `89.108.70.185`, Ubuntu, nginx, SSL через certbot
  (автопродление настроено certbot'ом). Раз в 10 минут делает
  `git pull origin main` в `/var/www/myavto-agregator` (cron на самом VPS).
- **GitHub Pages**: остаётся как есть, обновляется автоматически при пуше.
- **Агент и автоматизация** (поиск компаний, обновление сайта) — по-прежнему
  **на Маке**, не на VPS. Работает через `daily_update.sh` + cron
  (`crontab -l` на Маке: `0 8 * * * ~/myavto-agregator/daily_update.sh`).
  Пуш в GitHub — по SSH-ключу, passphrase в Keychain
  (`ssh-add --apple-use-keychain`), поэтому работает без участия человека.

## Конвенция: именованная версия перед fix-скриптами (10.08.2026)
Google Таблица — настоящий источник данных (не git, не index.html — тот
просто перегенерируется ИЗ таблицы через update_site.py). Значит откатить
git-коммит НЕ откатывает данные — при следующем update_site.py всё
перезапишется снова из таблицы. Единственный полноценный откат — версия
самой таблицы.

Поэтому перед любым точечным fix-скриптом (не обычным `company_agent.py`,
а разовыми правками/удалениями вроде `fix_dryrun_findings_batch1.py`)
Claude должен НАПОМИНАТЬ первой строкой инструкции: сначала поставить
именованную версию в Google Sheets — Файл → История версий → Назвать
текущую версию → название вроде «до <имя_скрипта>» → Сохранить. Если
что-то пойдёт не так — Файл → История версий → Открыть журнал версий →
выбрать версию → Восстановить эту версию, потом `python3 update_site.py`.

## Конвенция: находки — сразу в алгоритм агента, не только в разовый fix (14.08.2026)
По прямой просьбе пользователя ("все находки и навыки добавляй в
алгоритмы агента", "каждый день улучшай навыки агента, зафиксируй в
PROJECT_STATE.md"): когда в ходе сессии (ручная проверка сайта компании,
разбор бага, живой репорт от пользователя) всплывает что-то, что
`company_agent.py`/сопутствующие скрипты СЕЙЧАС не умеют находить или
отличать сами — недостаточно почитить только конкретную запись
разовым fix-скриптом. Нужно ещё и обновить сам алгоритм (регэксп, эвристику,
классификатор), чтобы то же самое ловилось автоматически на следующих
прогонах, без повторного ручного разбора. Разовый fix-скрипт чинит ПРОШЛОЕ
(уже испорченные/неполные строки), правка алгоритма чинит БУДУЩЕЕ (новые
компании, которые агент найдёт сам). Каждая такая правка должна быть
задокументирована здесь, в PROJECT_STATE.md, в тот же день.

Важно (см. также ниже про "другие направления"): такие правки должны быть
универсальными, не завязанными жёстко на нишу "импорт авто" — агент
позже будет использоваться и для других направлений (таможенные брокеры
уже в планах, возможны и другие), поэтому эвристики вроде "это канал или
личный контакт" пишутся как общие принципы (какие слова людям на сайтах
обычно означают "напишите мне" против "подпишитесь на канал"), а не как
список выражений, специфичных для авто-тематики.

Пример полного цикла (14.08.2026, см. также разделы про ТамСямAUTO и
email ниже): пользователь пожаловался на неработающую ссылку → разбор
показал системную причину (Instagram как единственный контакт) →
одновременно нашлись 3 независимых пробела в алгоритме (WhatsApp-ссылки
формата api.whatsapp.com не ловились вообще; агент не отличал
Telegram-канал от личного контакта на этапе ПЕРВОГО добавления компании,
только постфактум отдельным скриптом; `fix_telegram_contact_check.py`
классифицировал контакт грубее, чем можно) → все три исправлены в коде
`company_agent.py`/`fix_telegram_contact_check.py` в тот же день (см.
раздел "Улучшения алгоритма агента" ниже), не только в точечном
fix-скрипте для конкретных 7 компаний.

## Ключевые файлы (в папке myavto-agregator)
- `index.html` — сам сайт, один файл (HTML+CSS+JS), данные компаний зашиты
  прямо в JS-массив (генерируется скриптом, руками не редактировать).
- `update_site.py` — тянет данные из Google Sheets, гоняет ЕГРЮЛ-проверку,
  пересобирает `index.html`, коммитит и пушит.
- `company_agent.py` — ищет новые компании (tgstat.ru + DuckDuckGo),
  добавляет строки в Google Sheet. Извлекает ИНН со страниц компаний.
- `verify_egrul.py` — проверка компании по ИНН (ЕГРЮЛ/ЕГРИП). Источник 1 —
  DaData API (нужен токен), источник 2 — egrul.itsoft.ru (на 08.08.2026
  стабильно отдаёт 403, фактически не работает). Результаты кэшируются в
  `egrul_cache.json`.
- `backfill_inn.py` — разовый скрипт, добивает ИНН для старых компаний,
  у которых его не было при первом добавлении.
- `daily_update.sh` — обёртка для cron: агент → update_site → пуш.
- `agent_config.env` — **секреты, в git не попадает** (см. `.gitignore`):
  `GOOGLE_API_KEY`, `SEARCH_ENGINE_ID`, `SHEET_ID`, `DADATA_TOKEN`.
- `credentials.json` — сервисный аккаунт Google (для gspread), тоже в
  `.gitignore`, в git не попадает.
- `egrul_cache.json` — кэш проверок ЕГРЮЛ, **в git попадает** (это ОК,
  не секрет, просто данные).
- `favicon.ico` / `favicon-32.png` / `apple-touch-icon.png` — иконка сайта
  (логотип агрегатора — глобус с машиной, вырезан из полного лого).
  Старый `favicon.svg` (364КБ, чужое фото) больше не используется, но
  оставлен в репозитории (не мешает).

## Баг: update_site.py читал устаревший кэш Google Sheets — исправлено 09.08.2026
`update_site.py` раньше читал данные через публичный `gviz/tq` JSON-эндпоинт
(`docs.google.com/.../gviz/tq?tqx=out:json`) — у него есть собственный
серверный кэш на стороне Google, никакими заголовками с нашей стороны
(`Cache-Control`, случайный query-параметр) на него не повлиять. Если
запустить `update_site.py` сразу после того, как `company_agent.py`
дописал новые строки через gspread, можно словить устаревший снепшот. Это
не разовая случайность: `daily_update.sh` (cron) запускает оба скрипта
подряд без паузы — баг повторялся бы КАЖДЫЙ день, "теряя" сегодняшние
добавления до следующего прогона.

Исправлено: `update_site.py` теперь читает таблицу тем же способом, что и
`company_agent.py` — авторизованный `gspread` (сервисный аккаунт,
`credentials.json`) вместо публичного gviz-эндпоинта. У прямого API-чтения
через gspread кэширующего слоя нет. Заодно упростился код — раньше был
отдельный костыль под float-артефакт ИНН из gviz ("6234062211" →
"6234062211.0"), gspread отдаёт значения как обычные строки, костыль убран
за ненадобностью.

Из-за этого бага 14 компаний, добавленных первым прогоном с новыми
поисковыми фразами (SELLING_PHRASES), могли не попасть на сайт с первого
раза — нужно перепрогнать `python3 update_site.py` ещё раз с исправленной
версией, чтобы убедиться, что все 66 (52+14) компаний реально попали на
сайт.

## Баг со сдвигом колонок в append_row — исправлено 09.08.2026 (важно!)
Настоящая причина расхождения "52 vs 82 строки" оказалась НЕ в кэше gviz (тот
фикс тоже полезен, но не был корнем проблемы). Реальная причина: `ws.append_row()`
в `add_company()` вызывался БЕЗ `table_range='A1'`. Sheets API в этом случае
сам решает, где начинается "таблица", и в какой-то момент начал считать, что
она шире, чем колонка A — каждая следующая добавленная компания уезжала
вправо ещё дальше (реально наблюдали сдвиг 20 -> 44 -> 67 -> 89 -> 112
колонок). Итог: 29 из ~34 добавленных компаний физически лежали в таблице,
но в чужих колонках (61-86 вместо A-Z) — `update_site.py` их не видел
вообще, а Google Sheets UI показывал их как "пустые" строки в начале
просмотра.

Фикс: `add_company()` теперь всегда вызывает `ws.append_row(row, table_range='A1')`
— это лечит баг навсегда для новых добавлений.

Восстановление уже испорченных строк — `fix_column_shift_bug.py` (разовый,
уже отработал): для каждой "сломанной" строки находит первую непустую
ячейку (это и есть начало сдвинутого 26-колоночного блока), вырезает его,
чинит совсем битые названия вида "Telegram: View @username" через
`fetch_telegram_preview()`, режет обрубленные хвосты "Название (@handle...",
убирает дубли по имени, удаляет испорченные строки и дописывает чистые уже
через `table_range='A1'`. Восстановил 20 из 29 (9 отсеялось как дубли).

## Дубли по домену и рекламные заголовки вместо названий — исправлено 09.08.2026
После восстановления обнаружилось: часть "восстановленных" названий — это
не бренды, а рекламные SEO-заголовки страниц ("Купить новое авто с
доставкой" вместо реального "GazTormoz", "Японский аукцион автомобилей
Toyota из Японии" вместо "ПримАвто"). Плюс несколько записей оказались
дублями одной и той же компании, найденной дважды с разных подстраниц
одного домена (japantransit.ru и japantransit.ru/japan/auctions — как две
разные "компании"), а также дублями уже существовавших в каталоге компаний
(shapcars.ru, westmotors.ru).

Разобрал вручную (открыл каждый сайт), исправил конкретные записи через
`fix_generic_names_final.py`, и — что важнее — исправил САМ АЛГОРИТМ в
`company_agent.py`, чтобы это не повторялось:
1. `extract_brand_from_site(html)` — новая функция, вытаскивает настоящий
   бренд со страницы сайта через `og:site_name` или
   `apple-mobile-web-app-title` (подтверждено вручную: gaztormoz.ru отдаёт
   og:site_name="GazTormoz", tokidoki.su — apple-mobile-web-app-title=
   "ТокиДоки"). Приоритет имени теперь: бренд с сайта > заголовок из выдачи
   (`clean_name_from_title`) > домен как последний fallback.

## Content-верификация ссылок — исправлено 09.08.2026 (важно)
Пользователь лично прошёлся по нескольким карточкам на сайте и нашёл ещё

фирму). Причина: `find_platform_link()` подтверждал совпадение только по
СНИППЕТУ из поисковой выдачи DDG — а сниппет может быть неточным/обрезанным
и формально "совпасть" по случайному общему слову, хотя реальная страница
назначения — про другую компанию.

Исправлено в `company_agent.py`: добавлена `fetch_page_signal_text(url)` —
фетчит саму страницу-назначение (og:title/og:description + весь текст).
`find_platform_link()` теперь двухступенчатый: сначала дешёвый
предварительный фильтр по сниппету (как раньше), а затем ОБЯЗАТЕЛЬНАЯ
финальная проверка по РЕАЛЬНОМУ содержимому страницы назначения — оба шага
должны пройти, иначе ссылка не возвращается. Это касается всех типов
ссылок (карты/соцсети/маркетплейсы), т.к. все они идут через одну и ту же
функцию.

Разовая полная ре-верификация уже сохранённых ссылок по всему каталогу —
`fix_full_content_reverify.py` (на замену/в дополнение к более раннему
`fix_reverify_all_links.py`, который ловил только явно "не карточки" по
формату URL). Долгий скрипт (до 8 фетчей на компанию), может почистить
больше, чем ожидается, если какая-то площадка блокирует бота при фетче
(Instagram/VK иногда отдают заглушку вместо реальной страницы без логина)
— тогда валидная ссылка тоже может быть расценена как неподтверждённая и
очищена. Это осознанный компромисс в пользу честности (лучше не показать
кнопку, чем показать неверную), но при большом количестве "исчезновений"
после прогона стоит перепроверить вручную, не бот ли блокируется, а не
реальное несовпадение.

Первый прогон `fix_full_content_reverify.py` (09.08.2026) сам вскрыл ещё
один баг: VK отдаёт ботам заглушку "включите JavaScript" по адресу
"vk.com/js" вместо реальной страницы — эта заглушка ошибочно "подтвердила"
совпадение сразу для 4 РАЗНЫХ компаний (Worldcar, OTRADACARS, Jplife,
ТокиДоки), т.к. is_real_profile_url её не отсекала. Аналогично проскочили
"vk.com/video"/"vk.com/clips" (общие разделы сайта, без ID — старый regex
ловил только "video-123" с цифрой сразу после дефиса, а не голое "video")
и "instagram.com/favicon.ico" (иконка сайта). Исправлено: `VK_RESERVED_PATHS`
и `INSTAGRAM_RESERVED_PATHS` в `company_agent.py` — списки служебных
путей, которые никогда не могут быть профилем компании. Разовая чистка уже
записанного мусора — `fix_bad_reserved_paths.py`.

Вывод на будущее: при верификации по содержимому страницы назначения
нужно быть готовым, что сама страница может быть НЕ страницей ошибки в
привычном смысле (404/403), а специальной "заглушкой для ботов" с кодом
200 и генерическим содержимым — такая заглушка пройдёт любую проверку "не
пустой ли текст", поэтому важно ещё на уровне URL отсекать заведомо
служебные пути, не полагаясь только на content-check.

Сразу после первого прогона `fix_backfill_from_sources.py` пользователь
заметил "мусор" — 2ГИС у **MY Avto (id:1, компания САМОГО АВТОРА!)** и у
Winner Auto Club снова вели на ДРУГИЕ компании. Проверил лично:
`2gis.ru/vladivostok/firm/70000001110946107` — точно не MY Avto.

Причина: `_name_key(name)` брала просто первое слово названия для сверки
"это точно та компания?" в чужом тексте. Для "MY Avto" это было "my" —
обычное английское слово, встречается почти на любой странице с
английским текстом; для "Winner Auto Club" — "winner", тоже частое слово
(казино/ставки/реклама). При автопоиске недостающей карточки 2ГИС в
`fix_backfill_from_sources.py` (`find_platform_link`) это дало ложное
"подтверждение" случайной чужой карточки. А раз карточка была принята —
`backfill_from_sources` каскадно растащил из неё же и ДРУГИЕ пустые поля
(vk/instagram/telegram/avito/drom/autoru/max/youtube/rutube/whatsapp).
Один неверный "якорь" заразил сразу несколько полей одной компании —
именно поэтому "мусора добавилось" сразу много, а не одно поле.

Исправлено в `company_agent.py`: `_name_key()` теперь, если первое слово
короче 4 символов ИЛИ входит в список общеупотребимых слов
(`_GENERIC_NAME_WORDS`: my, auto, avto, trade, group, express, asia,
winner, premium и т.п.), берёт сочетание первых ДВУХ слов ("my avto",
"winner auto", "asia express") — гораздо специфичнее, случайно на чужой
странице не совпадёт. Это исправление автоматически подхватывается
ВЕЗДЕ, где используется `_name_key` (find_map_links/find_social_links/
find_marketplace_links/find_platform_link/fix_reverify_after_key_fix.py) —
никаких отдельных правок в местах вызова не нужно.

Разовая чистка — `fix_reverify_after_key_fix.py`: явно чистит
подтверждённый мусор у MY Avto, затем проходит по ВСЕМ ОСТАЛЬНЫМ
компаниям и переверяет ВСЕ уже сохранённые ссылки-площадки уже
исправленным строгим ключом, чистит неподтверждённое, пробует найти
подтверждённую замену.

**Дополнительная защита**: MY Avto (id:1) теперь явно ИСКЛЮЧЕНА из
`fix_backfill_from_sources.py` (и из общего прохода в

данными, подтверждёнными лично владельцем, а не автоматической проверкой

профиль/группа/канал принадлежит ровно одной компании, повтор почти
наверняка означает общий технический артефакт (виджет/пиксель/заглушка),
а не одинаковый настоящий аккаунт у двух разных фирм. Это универсальная
подстраховка сверх точечных чёрных списков — стоит гонять периодически
(например, вместе с `fix_reverify_after_key_fix.py`) как быструю проверку
на подобные "залипания".

(через `extract_social_from_text`/`extract_direct_contacts`/
`extract_extra_contacts_from_text`) без последующей content-проверки —
рискованный источник, потому что виджеты/пиксели рекламных площадок
выглядят как обычные ссылки на профиль этой же площадки. Точечные списки
зарезервированных путей ловят уже встреченные случаи, но dedup-проверка
(значение повторяется у нескольких компаний) — куда более надёжный общий
сигнал "это не настоящий профиль".

## Мусор от безнадзорного крона (10.08.2026) — 5 багов за один ночной прогон
Один прогон `company_agent.py` по крону (без ревью человеком перед
`update_site.py` + `git push`) добавил 5 плохих строк за раз. Разобрали
и починили в коде каждый случай (`fix_cron_bad_rows.py` чинит уже
попавшие в таблицу данные):
- **SonarBot** — бот/сервис ПРОВЕРКИ авто по VIN/госномеру, чужая ниша, но
  текст про "авто" в изобилии обманул старые фильтры. Добавлена
  `is_vin_check_service(text)` — отсекает по комбинации "бот"/"сервис
  проверки" + лексика пробива (vin-check, госномер, автокриминалист и т.п.).
- **Telagon** — блогерский/юридический канал, хостится на telagon.io
  (площадка аналитики telegram-каналов, не сайт компании). Добавлен в
  `BLACKLIST`.
- **tenchat.ru** — агент принял статью в блог-платформе tenchat.ru за
  карточку компании (в name попал заголовок статьи целиком). Добавлен в
  `BLACKLIST`.
- **Баг кодировки** — `fetch_site_text()` не проверял, объявил ли сервер
  `charset` в заголовке `Content-Type`; без явного charset `requests` по
  старому HTTP-стандарту декодирует как ISO-8859-1, что превращает
  UTF-8-кириллицу в мусор (например "АИ Авто" → "ÐÐ ÐÐ²ÑÐ¾"). Реальная
  компания ai-import.ru пострадала именно так — name стал нечитаемым.
  Фикс: если в `Content-Type` нет `charset`, берём `r.apparent_encoding`.
- **Название-слоган вместо имени** — если у сайта нет чёткого разделителя
  в `<title>` (тире/пайп и т.п.) и нет `og:site_name`, старый код брал весь
  `<title>` как есть. У autoshoot.ru title — рекламная фраза ("Подбор,
  покупка и доставка авто из Европы под ключ"), она и попала в name.
  Добавлена `is_probably_tagline(text)` (длиннее 35 симв. или больше 4
  слов → это не название) — `clean_name_from_title()` в таком случае
  возвращает "", и вызывающий код падает обратно на имя по домену.

Результат разбора: SonarBot/Telagon/tenchat.ru-статья — не наша ниша,
удалены. ai-import.ru — реальная компания "АИ Авто" (подтверждено
пользователем и `og:site_name` на сайте), name исправлен, остальные поля
были верными. autoshoot.ru — реальная компания, но отдельного бренда
кроме домена не нашлось (нет `og:site_name`), name исправлен на
"AutoShoot" по домену.

  успешной оплаты).
- `submitMassRequest(event)` — валидирует обязательные поля, вызывает
  `cloudPaymentsCheckout`, затем (тем же паттерном, что уже есть в
  `submitForm()` для заявок на размещение) открывает Telegram-бота
  `t.me/My_Avto_Agregator` с готовым текстом заявки — то есть реально
  работающий сквозной поток "заполнил → заявка ушла", просто без
  настоящего платежа внутри.
Протестировано через jsdom (заполнение формы, submit, проверка
открываемого URL и валидации) — работает.

Следующий шаг (когда будут реквизиты CloudPayments): заменить тело
`cloudPaymentsCheckout()` на реальный вызов виджета; отдельно ещё нет
бэкенда, который бы РЕАЛЬНО рассылал заявку N компаниям (сейчас имитация

## Сайдбар "Направление"/"География СНГ" и кнопка поиска были декоративными (10.08.2026)
Пользователь сообщил: "направления галочку ставишь фильтрация не
происходит". Разбор `index.html` показал три отдельных бага, все — в
JS-обвязке (не в данных):
1. Сайдбар "Направление" (`<aside class="sidebar">`) — чекбоксы `<input
   type="checkbox">` были ни к чему не подключены (ни одного addEventListener
   вообще), а числа рядом ("Китай (89)", "Корея (76)"...) — просто
   ЗАШИТЫЕ В HTML выдуманные цифры, не связанные с реальными данными
   (реально на тот момент: Китай 28, Корея 27 и т.д.). Это отдельная,
   ДРУГАЯ UI-секция, чем рабочие чипы-кнопки "🌍 Все направления" в шапке
   (`.dir`, у них есть `filterDir()`+`applyFilters()` и они РЕАЛЬНО
   фильтровали) — пользователь, скорее всего, кликал именно по сайдбару.
2. "География СНГ" (`.geo-item`) — обработчик клика СУЩЕСТВОВАЛ, но только
   переключал CSS-класс `.active` (подсветку), никогда не вызывал
   `applyFilters()`/`renderCompanies()` — визуально "что-то происходит",
   а список компаний не менялся вообще.
3. Кнопка "Найти компанию" / Enter в главном поиске (`doSearch()`) —
   показывала `alert('...в реальной версии здесь будет фильтрация
   каталога')` — буквальная заглушка-плейсхолдер, показанная реальным
   пользователям. При этом ввод текста в поле уже фильтровал вживую
   (отдельный `input`-listener) — баг был только в кнопке/Enter.

Причина у всех трёх одна: HTML/JS для этих элементов, видимо, писались
раньше основной логики фильтрации (`applyFilters`/`renderCompanies`/
`COMPANIES`) и остались недоделанными — заготовка/мокап, который никогда
не подключили к настоящим данным. Более того, в файле было ДВА разных
`<script>`-блока с функцией `filterDir` — ранний (просто подсвечивал,
ничего не фильтровал) и поздний (настоящий, с `applyFilters()`) —
поздний переопределял ранний, поэтому шапка-чипы всё же работали, а
дублирующий мёртвый код только путал.

Исправлено: сайдбар-чекбоксы получили `data-dir="..."` атрибуты и
реальный множественный выбор (объединяется с шапкой и поиском через общий
`applyFilters()`); geo-item получили `data-geo="..."` и реальную фильтрацию
по `c.region` (подстрокой, т.к. region — свободный текст вроде "Москва,
вся Россия"), плюс добавлен пункт "🌍 Все страны" (сброс); все счётчики
теперь считаются из `COMPANIES.length` на `DOMContentLoaded`, а не
захардкожены; `doSearch()` теперь вызывает `applyFilters()` +
`scrollIntoView` вместо alert-заглушки. Мёртвый ранний `filterDir` и
нерабочий geo-item-обработчик удалены. Протестировано через jsdom
(симуляция кликов/change-событий, сверка итогового числа карточек и
подписей счётчиков) — все сценарии дают верный результат.

Важно: `update_site.py` трогает только блок `const COMPANIES = [...]` и
две цифры в `.stat-n` — весь остальной HTML/CSS/JS (в т.ч. этот фикс)
редактируется вручную и update_site.py его не перезатирает.

## НАСТОЯЩАЯ причина "бот не отвечает" — слипшиеся строки в bot_config.env (12.08.2026, решено)
Весь предыдущий разбор (poll_loop падал молча, буферизация stdout) был
правильным по сути по общей устойчивости кода, но НЕ был корневой
причиной именно этого случая. Добавленная диагностика
(`sys.stdout.reconfigure(line_buffering=True)` + явные print до/после
`getUpdates`) сразу показала настоящую причину: в логе появилось
`proxies=None` и следом `getUpdates ошибка: ... Network is unreachable`
— то есть приложение вообще не использовало прокси, хотя он был
настроен и проверен рабочим отдельно.

`cat -A bot_config.env` на VPS показал: строка `PROXY_URL=...` слиплась
с предыдущей `BOT_USERNAME=` В ОДНУ строку —
`BOT_USERNAME=PROXY_URL=http://user431760:0d49u6@176.101.63.220:2470`
(в `nano` при добавлении строки курсор, похоже, остался в конце
`BOT_USERNAME=...` вместо новой строки). Следствие: ключа `PROXY_URL` в
файле не было вообще (`BOT_CONFIG.get("PROXY_URL","")` → пусто →
`PROXIES=None` → прямое соединение → `Network is unreachable`, та же
блокировка VPS↔Telegram, с которой всё начиналось), а `BOT_USERNAME`
стал битым мусором вместо `MyAvtoAgregator_bot` — это же, скорее всего,
объясняет и более ранний баг "форма массовой заявки открывала
telegram.org" (битое имя бота в диплинке `t.me/<мусор>?start=...`).

Исправлено: файл `bot_config.env` перезаписан целиком через `cat >
... << 'EOF'` (не `nano`, чтобы не словить ту же ошибку) с тремя
отдельными строками `BOT_TOKEN`/`BOT_USERNAME`/`PROXY_URL`. После рестарта бот

## Баг: window.open() блокировался браузером в форме массовой заявки — исправлено (12.08.2026)
Живой тест с пользователем (форма "Разослать запрос всем компаниям",
990 ₽): заявка на бэкенде создавалась успешно (`POST /api/mass-request`
→ 200, `bot_state.json` пополнялся), но Telegram не открывался — "нажал
отправить, ничего не произошло". Прокси и бэкенд тут ни при чём (это
проверили отдельно и оба оказались рабочими, см. записи выше) — баг был
в JS на сайте.

Причина: `window.open(...)` в `submitMassRequest()` вызывался ВНУТРИ
`.then()` после `fetch()`, то есть асинхронно — к моменту, когда сервер
отвечает, браузер уже не считает это "прямым результатом клика
пользователя" и тихо блокирует всплывающее окно (Safari/Chrome), без
видимой ошибки. `submitForm()` (форма добавления в каталог) этим не
страдает — там `window.open()` синхронный, сети не ждёт.

Исправлено: вкладка открывается СРАЗУ по клику (`window.open("", "_blank")`,
ещё до `fetch`), а адрес в неё (`tgWindow.location.href = ...`)
подставляется уже после ответа сервера — и в успешном пути, и в
fallback-пути. Так браузер видит window.open() как прямой результат
клика и не блокирует. Не протестировано автоматически (jsdom не эмулирует
блокировку всплывающих окон) — нужна ещё раз живая проверка на сайте:
заполнить форму массовой заявки и убедиться, что вкладка с Telegram
открывается.

## Ранжирование компаний на сайте (14.08.2026)
До этого порядок карточек = порядок строк в Google Таблице, никакой
сортировки не было (см. раздел выше про ElectroCar). Пользователь
попросил продумать нормальное ранжирование. Согласовали приоритет:

1. featured (ручной буст, TRUE у MY Avto и у точечно поднятых компаний
   вроде ElectroCar).
2. Онбордилась ли компания в Telegram-боте (нажала /start) — теперь не
   только даёт приоритет в заявках, но и поднимает в каталоге, доп.
   стимул откликнуться на email/TG-рассылку.
3. Подтверждена ли в ЕГРЮЛ (egrulVerified).
4. "Активность" — количество заполненных площадок (сайт, соцсети,
   маркетплейсы, карты, наличие отзывов) — по прямому уточнению
   пользователя ("для остальных индикатор активностей на сайте,
   соцсетях, маркетплейсах, картах, отзывах"). Рейтинг (rating/reviews
   как число) сознательно НЕ используется отдельным сигналом — у
   большинства компаний это непроверенная заглушка 4.5/0 (см. "Известные
   ограничения"), сортировка по нему была бы нечестной.

Внутри каждого уровня — стабильный порядок (сохраняется текущий порядок
строк), это гарантирует Array.sort в современных браузерах.

Реализация — новое поле `onboarded` пришлось провести через всю цепочку,
т.к. статус онбординга живёт в bot_state.json на VPS, а не в таблице:
- `add_onboarded_column.py` — заводит колонку 33 (AG) "Онбордился в боте".
- `sync_onboarded_to_sheet.py` — переносит статус из bot_state.json в эту
  колонку (запускать на VPS, где bot_state.json всегда свежий, либо
  скопировать файл на Мак через scp). Никогда не откатывает TRUE обратно
  в FALSE (осторожность на случай временного сбоя файла).
- `update_site.py` — читает колонку 33 (val(32)), добавляет
  `onboarded:true/false` в JS-объект каждой компании.
- `index.html` — `activityScore()` + `compareCompanies()` +
  `renderCompanies()` теперь сортирует список перед рендером
  (`[...list].sort(compareCompanies)`), а не показывает как есть.

Порядок запуска для полного применения: add_onboarded_column.py (один
раз) → sync_onboarded_to_sheet.py → update_site.py. Синхронизацию
онбординга стоит гонять периодически (не только один раз) — предложено
пользователю добавить в cron на VPS рядом с существующим git pull.
