## Что это
Публичный агрегатор компаний по импорту авто в СНГ (Китай, Корея, Япония, США,
ОАЭ, Европа). Сайт: myavto-agregator.ru. Репозиторий: GitHub
`lesnikovmn-svg/myavto-agregator` (публичный).

## Архитектура
Google Sheets (база данных) → Python-скрипты на Маке → генерируют встроенный
JS-массив в `index.html` → git push → GitHub Pages (основной источник) +
VPS REG.ru (зеркало, отдаёт сайт для рунета/Яндекса).

## Инфраструктура
- **Домен**: myavto-agregator.ru, регистратор и DNS — REG.ru.
- **VPS**: REG.ru, IP `89.108.70.185`, Ubuntu, nginx, SSL через certbot
  (автопродление настроено certbot'ом). Раз в 10 минут делает
  `git pull origin main` в `/var/www/myavto-agregator` (cron на самом VPS).
- **GitHub Pages**: остаётся как есть, обновляется автоматически при пуше.
- **Агент и автоматизация** (поиск компаний, обновление сайта) — по-прежнему
  **на Маке**, не на VPS. Работает через `daily_update.sh` + cron
  (`crontab -l` на Маке: `0 8 * * * ~/myavto-agregator/daily_update.sh`).
  Пуш в GitHub — по SSH-ключу, passphrase в Keychain
  (`ssh-add --apple-use-keychain`), поэтому работает без участия человека.

## Конвенция: именованная версия перед fix-скриптами (10.08.2026)
Google Таблица — настоящий источник данных (не git, не index.html — тот
просто перегенерируется ИЗ таблицы через update_site.py). Значит откатить
git-коммит НЕ откатывает данные — при следующем update_site.py всё
перезапишется снова из таблицы. Единственный полноценный откат — версия
самой таблицы.

Поэтому перед любым точечным fix-скриптом (не обычным `company_agent.py`,
а разовыми правками/удалениями вроде `fix_dryrun_findings_batch1.py`)
Claude должен НАПОМИНАТЬ первой строкой инструкции: сначала поставить
именованную версию в Google Sheets — Файл → История версий → Назвать
текущую версию → название вроде «до <имя_скрипта>» → Сохранить. Если
что-то пойдёт не так — Файл → История версий → Открыть журнал версий →
выбрать версию → Восстановить эту версию, потом `python3 update_site.py`.

## Ключевые файлы (в папке myavto-agregator)
- `index.html` — сам сайт, один файл (HTML+CSS+JS), данные компаний зашиты
  прямо в JS-массив (генерируется скриптом, руками не редактировать).
- `update_site.py` — тянет данные из Google Sheets, гоняет ЕГРЮЛ-проверку,
  пересобирает `index.html`, коммитит и пушит.
- `company_agent.py` — ищет новые компании (tgstat.ru + DuckDuckGo),
  добавляет строки в Google Sheet. Извлекает ИНН со страниц компаний.
- `verify_egrul.py` — проверка компании по ИНН (ЕГРЮЛ/ЕГРИП). Источник 1 —
  DaData API (нужен токен), источник 2 — egrul.itsoft.ru (на 08.08.2026
  стабильно отдаёт 403, фактически не работает). Результаты кэшируются в
  `egrul_cache.json`.
- `backfill_inn.py` — разовый скрипт, добивает ИНН для старых компаний,
  у которых его не было при первом добавлении.
- `daily_update.sh` — обёртка для cron: агент → update_site → пуш.
- `agent_config.env` — **секреты, в git не попадает** (см. `.gitignore`):
  `GOOGLE_API_KEY`, `SEARCH_ENGINE_ID`, `SHEET_ID`, `DADATA_TOKEN`.
- `credentials.json` — сервисный аккаунт Google (для gspread), тоже в
  `.gitignore`, в git не попадает.
- `egrul_cache.json` — кэш проверок ЕГРЮЛ, **в git попадает** (это ОК,
  не секрет, просто данные).
- `favicon.ico` / `favicon-32.png` / `apple-touch-icon.png` — иконка сайта
  (логотип агрегатора — глобус с машиной, вырезан из полного лого).
  Старый `favicon.svg` (364КБ, чужое фото) больше не используется, но
  оставлен в репозитории (не мешает).

## Баг: update_site.py читал устаревший кэш Google Sheets — исправлено 09.08.2026
`update_site.py` раньше читал данные через публичный `gviz/tq` JSON-эндпоинт
(`docs.google.com/.../gviz/tq?tqx=out:json`) — у него есть собственный
серверный кэш на стороне Google, никакими заголовками с нашей стороны
(`Cache-Control`, случайный query-параметр) на него не повлиять. Если
запустить `update_site.py` сразу после того, как `company_agent.py`
дописал новые строки через gspread, можно словить устаревший снепшот. Это
не разовая случайность: `daily_update.sh` (cron) запускает оба скрипта
подряд без паузы — баг повторялся бы КАЖДЫЙ день, "теряя" сегодняшние
добавления до следующего прогона.

Исправлено: `update_site.py` теперь читает таблицу тем же способом, что и
`company_agent.py` — авторизованный `gspread` (сервисный аккаунт,
`credentials.json`) вместо публичного gviz-эндпоинта. У прямого API-чтения
через gspread кэширующего слоя нет. Заодно упростился код — раньше был
отдельный костыль под float-артефакт ИНН из gviz ("6234062211" →
"6234062211.0"), gspread отдаёт значения как обычные строки, костыль убран
за ненадобностью.

Из-за этого бага 14 компаний, добавленных первым прогоном с новыми
поисковыми фразами (SELLING_PHRASES), могли не попасть на сайт с первого
раза — нужно перепрогнать `python3 update_site.py` ещё раз с исправленной
версией, чтобы убедиться, что все 66 (52+14) компаний реально попали на
сайт.

## Баг со сдвигом колонок в append_row — исправлено 09.08.2026 (важно!)
Настоящая причина расхождения "52 vs 82 строки" оказалась НЕ в кэше gviz (тот
фикс тоже полезен, но не был корнем проблемы). Реальная причина: `ws.append_row()`
в `add_company()` вызывался БЕЗ `table_range='A1'`. Sheets API в этом случае
сам решает, где начинается "таблица", и в какой-то момент начал считать, что
она шире, чем колонка A — каждая следующая добавленная компания уезжала
вправо ещё дальше (реально наблюдали сдвиг 20 -> 44 -> 67 -> 89 -> 112
колонок). Итог: 29 из ~34 добавленных компаний физически лежали в таблице,
но в чужих колонках (61-86 вместо A-Z) — `update_site.py` их не видел
вообще, а Google Sheets UI показывал их как "пустые" строки в начале
просмотра.

Фикс: `add_company()` теперь всегда вызывает `ws.append_row(row, table_range='A1')`
— это лечит баг навсегда для новых добавлений.

Восстановление уже испорченных строк — `fix_column_shift_bug.py` (разовый,
уже отработал): для каждой "сломанной" строки находит первую непустую
ячейку (это и есть начало сдвинутого 26-колоночного блока), вырезает его,
чинит совсем битые названия вида "Telegram: View @username" через
`fetch_telegram_preview()`, режет обрубленные хвосты "Название (@handle...",
убирает дубли по имени, удаляет испорченные строки и дописывает чистые уже
через `table_range='A1'`. Восстановил 20 из 29 (9 отсеялось как дубли).

## Дубли по домену и рекламные заголовки вместо названий — исправлено 09.08.2026
После восстановления обнаружилось: часть "восстановленных" названий — это
не бренды, а рекламные SEO-заголовки страниц ("Купить новое авто с
доставкой" вместо реального "GazTormoz", "Японский аукцион автомобилей
Toyota из Японии" вместо "ПримАвто"). Плюс несколько записей оказались
дублями одной и той же компании, найденной дважды с разных подстраниц
одного домена (japantransit.ru и japantransit.ru/japan/auctions — как две
разные "компании"), а также дублями уже существовавших в каталоге компаний
(shapcars.ru, westmotors.ru).

Разобрал вручную (открыл каждый сайт), исправил конкретные записи через
`fix_generic_names_final.py`, и — что важнее — исправил САМ АЛГОРИТМ в
`company_agent.py`, чтобы это не повторялось:
1. `extract_brand_from_site(html)` — новая функция, вытаскивает настоящий
   бренд со страницы сайта через `og:site_name` или
   `apple-mobile-web-app-title` (подтверждено вручную: gaztormoz.ru отдаёт
   og:site_name="GazTormoz", tokidoki.su — apple-mobile-web-app-title=
   "ТокиДоки"). Приоритет имени теперь: бренд с сайта > заголовок из выдачи
   (`clean_name_from_title`) > домен как последний fallback.
2. `domain_of(url)` — нормализует URL до голого домена. `get_existing()`
   теперь кладёт в множество "уже есть" не только имя/телеграм/полный
   URL, но и домен сайта — и DDG-цикл проверяет домен ДО похода на сайт
   (экономит запрос) и добавляет домен в `existing` после успешного
   добавления. Это лечит дубли "одна компания = разные подстраницы одного
   сайта = разные поисковые запросы".
3. Сайт теперь фетчится ОДИН раз (раньше — только для ИНН, после выбора
   имени; теперь — до выбора имени, тот же fetch переиспользуется и для
   ИНН/Украины).

## Ложная тревога с "удалёнными" компаниями — разобрано 09.08.2026
После прогона `fix_generic_names_final.py` (дедуп по домену) лог показал
кучу подозрительных "дублей" — например, «ПримАвто» как дубль домена
`vk.ru`, что бессмысленно (её настоящий домен prim-auto.com). Разбор
показал: в самом скрипте `fix_generic_names_final.py` был off-by-one баг
при печати имени/проверке ИНН для решения "кого удалить, кого оставить" —
использовался индекс `all_values[r - 2]` вместо `all_values[r - 1]`, из-за
чего в логе печаталось имя СОСЕДНЕЙ строки, а не той, что реально
проверялась/удалялась (сам номер строки на удаление был правильным —
баг был только в диагностическом выводе).

Проверили через `check_names_exist.py` (прямой поиск по текущей таблице,
без дедупа) — почти все "удалённые" на самом деле остались: AviAuto,
CarExport, ТокиДоки, Япония Транзит, EncarRus, LikeAvto — все на месте.
"ПримАвто" была настоящим дублем (в каталоге уже был `Prim-Auto`,
row31, тот же домен prim-auto.com) — удаление корректно. Единственная
реальная потеря — **AutoImport Russia** (ИНН 2508148924) — восстановлена
через `fix_final_restore_and_cleanup.py` с полными оригинальными данными
(взяты из более ранней корректно-проиндексированной диагностики
`debug_sheet_count3.py`, сделанной ДО того, как что-либо пошло не так).

Вывод для будущих одноразовых скриптов на этот проект: при удалении строк
из Google Sheets НИКОГДА не полагаться на печатаемое в моменте "имя" как на

очищена. Это осознанный компромисс в пользу честности (лучше не показать
кнопку, чем показать неверную), но при большом количестве "исчезновений"
после прогона стоит перепроверить вручную, не бот ли блокируется, а не
реальное несовпадение.

ловил только "video-123" с цифрой сразу после дефиса, а не голое "video")

и `INSTAGRAM_RESERVED_PATHS` в `company_agent.py` — списки служебных
путей, которые никогда не могут быть профилем компании. Разовая чистка уже
записанного мусора — `fix_bad_reserved_paths.py`.

Вывод на будущее: при верификации по содержимому страницы назначения
нужно быть готовым, что сама страница может быть НЕ страницей ошибки в
привычном смысле (404/403), а специальной "заглушкой для ботов" с кодом

служебные пути, не полагаясь только на content-check.

## Баг: слишком общий _name_key заразил MY Avto и Winner мусором — исправлено 09.08.2026 (важно!)
Сразу после первого прогона `fix_backfill_from_sources.py` пользователь
заметил "мусор" — 2ГИС у **MY Avto (id:1, компания САМОГО АВТОРА!)** и у
Winner Auto Club снова вели на ДРУГИЕ компании. Проверил лично:
`2gis.ru/vladivostok/firm/70000001110946107` — точно не MY Avto.

Причина: `_name_key(name)` брала просто первое слово названия для сверки
"это точно та компания?" в чужом тексте. Для "MY Avto" это было "my" —
обычное английское слово, встречается почти на любой странице с
английским текстом; для "Winner Auto Club" — "winner", тоже частое слово
(казино/ставки/реклама). При автопоиске недостающей карточки 2ГИС в
`fix_backfill_from_sources.py` (`find_platform_link`) это дало ложное
"подтверждение" случайной чужой карточки. А раз карточка была принята —
`backfill_from_sources` каскадно растащил из неё же и ДРУГИЕ пустые поля
(vk/instagram/telegram/avito/drom/autoru/max/youtube/rutube/whatsapp).
Один неверный "якорь" заразил сразу несколько полей одной компании —
именно поэтому "мусора добавилось" сразу много, а не одно поле.

Исправлено в `company_agent.py`: `_name_key()` теперь, если первое слово
короче 4 символов ИЛИ входит в список общеупотребимых слов
(`_GENERIC_NAME_WORDS`: my, auto, avto, trade, group, express, asia,
winner, premium и т.п.), берёт сочетание первых ДВУХ слов ("my avto",
"winner auto", "asia express") — гораздо специфичнее, случайно на чужой
странице не совпадёт. Это исправление автоматически подхватывается
ВЕЗДЕ, где используется `_name_key` (find_map_links/find_social_links/
find_marketplace_links/find_platform_link/fix_reverify_after_key_fix.py) —
никаких отдельных правок в местах вызова не нужно.

Разовая чистка — `fix_reverify_after_key_fix.py`: явно чистит
подтверждённый мусор у MY Avto, затем проходит по ВСЕМ ОСТАЛЬНЫМ
компаниям и переверяет ВСЕ уже сохранённые ссылки-площадки уже
исправленным строгим ключом, чистит неподтверждённое, пробует найти
подтверждённую замену.

**Дополнительная защита**: MY Avto (id:1) теперь явно ИСКЛЮЧЕНА из

(значение повторяется у нескольких компаний) — куда более надёжный общий
сигнал "это не настоящий профиль".

открываемого URL и валидации) — работает.

## Сайдбар "Направление"/"География СНГ" и кнопка поиска были декоративными (10.08.2026)
Пользователь сообщил: "направления галочку ставишь фильтрация не
происходит". Разбор `index.html` показал три отдельных бага, все — в
JS-обвязке (не в данных):
1. Сайдбар "Направление" (`<aside class="sidebar">`) — чекбоксы `<input
   type="checkbox">` были ни к чему не подключены (ни одного addEventListener
   вообще), а числа рядом ("Китай (89)", "Корея (76)"...) — просто
   ЗАШИТЫЕ В HTML выдуманные цифры, не связанные с реальными данными
   (реально на тот момент: Китай 28, Корея 27 и т.д.). Это отдельная,
   ДРУГАЯ UI-секция, чем рабочие чипы-кнопки "🌍 Все направления" в шапке
   (`.dir`, у них есть `filterDir()`+`applyFilters()` и они РЕАЛЬНО
   фильтровали) — пользователь, скорее всего, кликал именно по сайдбару.
2. "География СНГ" (`.geo-item`) — обработчик клика СУЩЕСТВОВАЛ, но только
   переключал CSS-класс `.active` (подсветку), никогда не вызывал
   `applyFilters()`/`renderCompanies()` — визуально "что-то происходит",
   а список компаний не менялся вообще.
3. Кнопка "Найти компанию" / Enter в главном поиске (`doSearch()`) —
   показывала `alert('...в реальной версии здесь будет фильтрация
   каталога')` — буквальная заглушка-плейсхолдер, показанная реальным
   пользователям. При этом ввод текста в поле уже фильтровал вживую
   (отдельный `input`-listener) — баг был только в кнопке/Enter.

Причина у всех трёх одна: HTML/JS для этих элементов, видимо, писались
раньше основной логики фильтрации (`applyFilters`/`renderCompanies`/
`COMPANIES`) и остались недоделанными — заготовка/мокап, который никогда
не подключили к настоящим данным. Более того, в файле было ДВА разных
`<script>`-блока с функцией `filterDir` — ранний (просто подсвечивал,
ничего не фильтровал) и поздний (настоящий, с `applyFilters()`) —
поздний переопределял ранний, поэтому шапка-чипы всё же работали, а
дублирующий мёртвый код только путал.

Исправлено: сайдбар-чекбоксы получили `data-dir="..."` атрибуты и
реальный множественный выбор (объединяется с шапкой и поиском через общий
`applyFilters()`); geo-item получили `data-geo="..."` и реальную фильтрацию
по `c.region` (подстрокой, т.к. region — свободный текст вроде "Москва,
вся Россия"), плюс добавлен пункт "🌍 Все страны" (сброс); все счётчики
теперь считаются из `COMPANIES.length` на `DOMContentLoaded`, а не
захардкожены; `doSearch()` теперь вызывает `applyFilters()` +
`scrollIntoView` вместо alert-заглушки. Мёртвый ранний `filterDir` и
нерабочий geo-item-обработчик удалены. Протестировано через jsdom
(симуляция кликов/change-событий, сверка итогового числа карточек и
подписей счётчиков) — все сценарии дают верный результат.

Важно: `update_site.py` трогает только блок `const COMPANIES = [...]` и
две цифры в `.stat-n` — весь остальной HTML/CSS/JS (в т.ч. этот фикс)
редактируется вручную и update_site.py его не перезатирает.
